# Mandatory-Files

A mandatory file is one the foundation declares must exist. The vault has two mandates: one at vault root (`CLAUDE.md`) and one per folder (`_index.md`). Both are structural — the system creates and maintains them on your behalf rather than depending on you to remember to author them. The intent is that the vault's contract documents are present by construction; you never face a missing-index advisory at audit time on a folder you wrote to a week ago.

The runtime contract is composed from the two artifacts that ship in `governance/`:

- **`foundation-master.json`** — the mandate set, the per-mandate body-structure contracts, and the exemption list.
- **`overlay-master.json`** — your registered exemption extensions and any overlay mandates you've added. Ships empty for mandates and exemption extensions.

## The vault-root mandate

The foundation ships exactly one vault-root mandatory file: `CLAUDE.md`. It's the vault's top-level contract — the first document Claude reads when it operates against your vault, naming the operational conventions, surfacing the system spokes, and orienting any session to the vault's current shape.

`CLAUDE.md` is the only mandated vault-root file. Foundation-mandated content lives in folders; everything else at vault root is either an explicit single-file exemption documented in the naming pillar ([[System Governance - Naming]]) or a placement advisory you triage.

Its body shape is governed by a file-type contract (see [[System Governance - File-Type-Contracts]]) — write-shape `create-only`, with the system honoring your edits via the contract's amender rather than wholesale overwrites.

## The per-folder mandate

Every non-exempt user-facing folder in the vault carries a sibling `_index.md` at folder root. The file serves two consumers at once:

- **For Claude.** When Claude reads a folder, `_index.md` gives it orientation in one read instead of N reads of every child file. Past about ten child files, walking a folder file-by-file becomes prohibitively expensive in tokens; past about fifty it stops being feasible.
- **For you.** When you open a folder in Obsidian, `_index.md` is the navigation hub — the folder's table of contents, a description of what lives there, and the contextual frame the folder operates in.

The mandate is structural rather than aspirational. When you write the first file to a non-exempt folder, the system auto-bootstraps an `_index.md` in that folder. You don't author the index by hand on day one — the index exists by the time the folder has a child.

Its body shape is governed by a file-type contract: H1 matching the folder name, a folder-context paragraph (2–4 sentences describing what the folder holds), and a contents-enum table with `File | Lines | Type | Description` columns wrapped in sentinel markers. The contract is the structural backbone the maintenance layers run against.

## The foundation exempt set

One folder is exempt from the `_index.md` mandate by foundation default:

| Folder | Why it's exempt |
|---|---|
| `Work/` | A symlink to your external work home (`~/work/`). Its spoke subfolders carry their own indexes — the `deliverables/_index.md` and `reference/_index.md` are generated by the librarian, and each spoke's `hub.md` is its cover page — so the mandate's auto-bootstrap would duplicate work the librarian already does. Deliverables are authored outside the vault root, so the bootstrap would not fire there anyway. |

The exemption set is a positive list — only the folders enumerated above are exempt. Any other folder you create, foundation-shipped or otherwise, carries the mandate. The auto-bootstrap fires on first write to it; the librarian sweep catches folders you created but haven't written to yet.

## Extending the exempt set

If you have a folder whose contents are machine-emitted, append-only, or otherwise structurally unsuitable for a navigation index, register the exemption via `/govern register --kind index-exemption`. The registration writes a path glob to `overlay-master.json` under `mandatory_files.mandates._index_md.exemption_paths`. The next write that matches the glob proceeds without bootstrapping an `_index.md`.

Adding a *new* documented vault-root folder is a different operation — that goes through the naming pillar's seven-item new-root checklist (see [[System Governance - Naming]]), which couples the root registration to the spoke update, the type registry, and the librarian capability layer in a single atomic commit.

## The three-tier maintenance architecture

The mandate is upheld by three independent layers that converge on the same property: every non-exempt folder has an `_index.md`, and every `_index.md` reflects its folder's current contents.

**Tier 1 — Live, on every write.** A post-write hook fires after every Edit / Write tool call. If the file lives in a non-exempt folder lacking an `_index.md`, the hook bootstraps the index. If the index exists, the hook reconciles the contents-enum table to add or update the row for the file you just wrote. A one-line self-exempt guard at the hook entry stops it from recursing on its own writes.

**Tier 2 — Periodic sweep.** A librarian capability walks the vault on `/librarian full` and on a scheduled cadence. It catches folders the live hook missed: hand-created folders that haven't been written to yet, files added through direct filesystem edits outside Claude's tool surface, drift in contents-enum row ordering. The sweep is mechanical — it fixes what can be derived from filenames and frontmatter and surfaces what can't.

**Tier 3 — Deep audit.** The same capability run with `--deep` walks the contents-enum descriptions and ordering and emits an opt-in semantic-validation report. Tier 3 is the only layer that touches author intent (description quality, ordering rationale); it stays opt-in by design so the mechanical layers don't quietly rewrite your prose.

The boundary between mechanical and semantic is the self-healing contract: the system mutates values it can derive without judgment (file presence, line counts, type fields). Anything that requires reading what a file *means* — its description, its position in the contents table, whether a path glob should be exempt — surfaces as a finding for you to review rather than auto-applied.

## What happens on write

Order of checks the system runs when you write a vault file:

1. **Self-exempt guard.** If the write target is itself an `_index.md`, the hook short-circuits — the maintenance machinery never recurses on its own emissions.
2. **Folder-exemption check.** The parent folder is matched against the union of foundation + overlay exemption paths. A match stops the auto-bootstrap; the file lands without an index being created.
3. **Index presence.** If the folder is non-exempt and lacks an `_index.md`, the hook bootstraps one against the body-structure contract.
4. **Contents-enum live-sync.** If the folder already has an `_index.md`, the hook updates its contents-enum row for the file just written (adding, updating, or leaving the row alone based on derivable values only).
5. **Audit-trail.** The librarian's periodic sweep is the safety net for everything the live hook missed.

## Anti-patterns

| Anti-pattern | What goes wrong | Better path |
|---|---|---|
| Hand-authoring `_index.md` on a folder you just created | The auto-bootstrap fires anyway on first child write and races with your hand-authored content. | Let the bootstrap create the file; edit afterward through the file's amender. |
| Deleting `_index.md` to suppress the mandate | The next write to the folder bootstraps the index again; the librarian sweep flags the deletion as a finding. | If the folder is genuinely indexless by design, register the exemption via `/govern register --kind index-exemption`. The waiver lands in the audit trail with rationale. |
| Editing the contents-enum table by hand | The post-write live-sync may overwrite your edits when it next reconciles the table against folder contents. | The contents-enum is mechanical: row presence, line counts, types are derived. Description and ordering are semantic — edit those through the amender, which knows which fields to preserve. |
| Treating the Tier 1 hook as the only mandate enforcement | The hook misses folders that exist but haven't been written to; direct-filesystem edits outside the tool surface bypass it entirely. | Run the librarian's `index-maintain` sweep periodically (or rely on the scheduled cadence). The three tiers are layered for a reason — none of them alone closes the gap. |
| Bypassing the mandate with a `.gitignored` placeholder | A `.gitignored` `_index.md` placeholder defeats both the auto-bootstrap and the librarian's audit; the folder appears compliant in git but isn't in your actual vault. | The mandate operates on the working tree, not on what gets committed. If the folder genuinely shouldn't have an index, register the exemption. |
